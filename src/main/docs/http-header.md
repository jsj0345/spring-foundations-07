# HTTP 헤더와 쿠키 복습

> 본문을 해석하는 표현 헤더, 콘텐츠 협상, 전송 정보, 쿠키의 역할을 구분해서 정리했다.

## 1. 헤더의 역할

HTTP 본문만으로는 데이터의 종류와 처리 방법을 모두 알기 어렵다. 헤더는 요청과 응답을 해석하는 데 필요한 메타 정보를 전달한다.

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 24

{"name":"spring"}
```

본문은 실제 표현 데이터이고 헤더는 그 데이터를 설명한다.

## 2. 표현 헤더

| 헤더 | 의미 |
|---|---|
| `Content-Type` | 표현의 미디어 타입과 문자 인코딩 |
| `Content-Encoding` | 압축 또는 인코딩 방식 |
| `Content-Language` | 표현에 사용된 자연어 |
| `Content-Length` | 본문의 바이트 길이 |

```http
Content-Type: text/html; charset=utf-8
Content-Encoding: gzip
Content-Language: ko
```

송신자는 어떤 방식으로 만들었는지 알려 주고 수신자는 그 정보에 맞춰 본문을 해석한다.

## 3. 콘텐츠 협상

클라이언트는 자신이 선호하는 표현 형식을 요청 헤더로 알릴 수 있다.

```http
Accept: application/json
Accept-Encoding: gzip
Accept-Language: ko-KR, ko;q=0.9, en;q=0.7
```

`q` 값은 선호도를 나타내며 값이 클수록 우선순위가 높다. 생략하면 가장 높은 선호도로 취급된다.

서버가 모든 형식을 제공한다는 보장은 없다. 서버가 지원하는 표현 중 요청 조건에 가장 잘 맞는 결과를 선택한다.

와일드카드보다 구체적인 조건이 우선될 수 있다.

```text
text/plain;format=flowed
→ text/plain
→ text/*
→ */*
```

## 4. 전송 방식

### 길이를 알고 한 번에 전송

```http
Content-Length: 3423
```

### 압축 전송

```http
Content-Encoding: gzip
```

### 분할 전송

```http
Transfer-Encoding: chunked
```

본문을 여러 덩어리로 보내므로 전체 길이를 미리 알 수 없고 일반적으로 `Content-Length`와 함께 사용하지 않는다.

### 범위 전송

```http
Range: bytes=1000-1999
```

파일의 일부만 다시 받거나 이어받을 때 사용할 수 있다.

## 5. 요청과 응답을 보조하는 헤더

- `Host`: 요청 대상 도메인
- `Referer`: 현재 요청으로 이동하기 전 페이지
- `User-Agent`: 브라우저나 클라이언트 정보
- `Server`: 응답한 원 서버 소프트웨어 정보
- `Location`: 생성된 리소스 또는 리다이렉션 대상
- `Allow`: 지원하는 HTTP 메서드
- `Retry-After`: 다시 요청하기 전에 기다릴 시간

하나의 IP가 여러 도메인을 서비스할 수 있으므로 `Host`는 서버가 올바른 가상 호스트를 선택하는 데 중요하다.

## 6. 무상태와 쿠키

HTTP 요청은 기본적으로 이전 요청의 사용자 문맥을 자동으로 포함하지 않는다.

로그인 응답에서 서버가 쿠키를 전달할 수 있다.

```http
Set-Cookie: sessionId=abc123; Path=/; HttpOnly
```

브라우저는 이후 조건에 맞는 요청에 쿠키를 보낸다.

```http
Cookie: sessionId=abc123
```

서버는 쿠키에 담긴 세션 식별자를 이용해 사용자 상태를 찾을 수 있다.

중요한 개인정보나 결제 정보를 쿠키 자체에 그대로 넣는 방식은 피해야 한다.

## 7. 쿠키와 캐시 비교

| 구분 | 쿠키 | 캐시 |
|---|---|---|
| 주된 목적 | 사용자 식별과 상태 연결 | 응답 재사용과 성능 향상 |
| 저장 내용 | 식별자, 설정값 등 작은 정보 | HTML, 이미지, API 응답 등 |
| 서버 전송 | 조건에 맞으면 요청마다 전송 | 유효하면 서버 요청 없이 사용 가능 |
| 주의점 | 보안과 전송량 | 오래된 데이터와 공유 범위 |

둘 다 브라우저에 저장될 수 있지만 해결하는 문제가 다르다.

## 8. 쿠키의 범위와 수명

```http
Set-Cookie: theme=dark; Max-Age=3600; Domain=example.com; Path=/
```

- `Expires`, `Max-Age`: 유지 기간
- `Domain`: 쿠키를 전송할 도메인 범위
- `Path`: 전송할 경로 범위
- 만료 정보 없음: 브라우저 세션 동안 유지되는 쿠키로 동작할 수 있음

범위를 넓게 지정할수록 더 많은 요청에 쿠키가 포함되므로 필요한 범위만 설정하는 편이 좋다.

## 9. 보안 관점에서의 한계

- 쿠키는 요청마다 전송되어 크기가 크면 네트워크 비용이 늘어난다.
- 브라우저에 보관되므로 민감한 원문 데이터를 저장하면 안 된다.
- JavaScript 접근이 필요 없다면 `HttpOnly`를 고려한다.
- HTTPS에서만 보내야 한다면 `Secure`를 사용한다.
- 교차 사이트 요청 정책에는 `SameSite` 설정도 함께 검토한다.

## 핵심 정리

- 헤더는 본문을 설명하고 요청·응답 처리 조건을 전달한다.
- 콘텐츠 협상은 클라이언트 선호도와 서버 지원 범위의 교집합이다.
- 전송 방식에 따라 길이, 압축, 분할, 범위 헤더가 달라진다.
- 쿠키는 무상태 HTTP 위에서 사용자 상태를 연결하는 수단이다.
- 쿠키와 캐시는 목적과 전송 방식이 서로 다르다.
