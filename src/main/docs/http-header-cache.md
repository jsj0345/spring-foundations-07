# HTTP 캐시와 조건부 요청 복습

> 캐시가 응답 속도를 높이는 과정과 만료 후 데이터를 다시 검증하는 방법을 정리했다.

## 1. 캐시가 없을 때

변경되지 않은 이미지에 매번 요청을 보내고 전체 파일을 다시 받으면 같은 네트워크 비용이 반복된다.

```text
요청
→ 서버에서 이미지 전체 전송
→ 다시 요청
→ 같은 이미지 전체 전송
```

데이터가 크거나 사용자가 많을수록 원 서버의 부하와 응답 시간이 증가한다.

## 2. 캐시 유효 시간

```http
Cache-Control: max-age=60
```

클라이언트는 응답을 저장한 뒤 60초 동안 새 요청 없이 재사용할 수 있다.

```text
처음 조회 → 서버 응답을 캐시에 저장
유효 시간 안 → 로컬 캐시 사용
유효 시간 종료 → 서버에 다시 확인
```

캐시는 서버 요청 횟수, 전송량, 화면 로딩 시간을 줄여 준다.

## 3. 만료와 변경 여부는 다른 문제

캐시가 만료됐다는 사실은 데이터가 실제로 바뀌었다는 뜻이 아니다.

만료 때마다 전체 본문을 다시 받으면 내용이 그대로인 경우에도 대용량 전송이 발생한다. 이를 줄이기 위해 클라이언트가 가진 버전과 서버 버전을 비교하는 조건부 요청을 사용한다.

## 4. 수정 시각으로 검증

서버 응답:

```http
Last-Modified: Tue, 10 Nov 2020 10:00:00 GMT
```

다음 요청:

```http
If-Modified-Since: Tue, 10 Nov 2020 10:00:00 GMT
```

변경되지 않았다면 서버는 본문 없이 응답할 수 있다.

```http
HTTP/1.1 304 Not Modified
```

클라이언트는 기존 본문을 계속 사용하고 응답 헤더를 기준으로 캐시 정보를 갱신한다.

날짜 기반 검증은 정밀도에 한계가 있고 내용이 원래 값으로 돌아온 경우처럼 실제 결과가 같아도 수정 시각만 달라질 수 있다.

## 5. ETag 검증

```http
ETag: "resource-v4"
```

클라이언트는 다음 요청에 태그를 전달한다.

```http
If-None-Match: "resource-v4"
```

태그가 같으면 `304`, 다르면 새 본문과 새로운 ETag를 받는다.

ETag를 어떻게 생성할지는 서버가 결정할 수 있어 날짜보다 내용 버전 중심으로 관리하기 쉽다.

## 6. 주요 Cache-Control 지시어

| 지시어 | 내가 이해한 의미 |
|---|---|
| `max-age` | 지정한 초 동안 캐시를 신선한 것으로 사용 |
| `no-cache` | 저장은 가능하지만 사용 전에 원 서버 검증 필요 |
| `no-store` | 응답을 저장하지 않도록 요청 |
| `must-revalidate` | 만료 후 원 서버 검증에 실패하면 오래된 응답을 임의 사용하지 않음 |
| `public` | 공유 프록시 캐시에 저장 가능 |
| `private` | 특정 사용자용 캐시에만 저장 |

`no-cache`는 캐시 금지가 아니라 재검증 요구라는 점이 이름 때문에 헷갈리기 쉽다.

## 7. 프록시 캐시

```text
클라이언트
→ 가까운 프록시 캐시
→ 원 서버
```

여러 사용자가 동일한 정적 리소스를 요청할 때 프록시가 응답을 보관하면 원 서버까지 가는 요청과 장거리 전송을 줄일 수 있다.

사용자별 개인정보가 포함된 응답을 공유 캐시에 저장하지 않도록 `public`, `private`와 인증 관련 정책을 신중하게 설정해야 한다.

## 8. 캐시를 확실히 남기고 싶지 않은 경우

민감한 응답은 다음과 같은 조합을 고려할 수 있다.

```http
Cache-Control: no-cache, no-store, must-revalidate
Pragma: no-cache
```

`Pragma`는 오래된 HTTP 환경과의 호환을 위한 용도로 함께 쓰일 수 있다.

캐시 정책은 브라우저뿐 아니라 중간 프록시와 CDN에도 영향을 줄 수 있으므로 응답 성격에 맞춰야 한다.

## 9. 설계 시 한계점

- 너무 긴 `max-age`는 변경 반영을 늦출 수 있다.
- 너무 짧으면 검증 요청이 자주 발생한다.
- ETag 계산도 서버 비용이 들 수 있다.
- 개인화 응답을 공유 캐시에 저장하면 정보가 섞일 위험이 있다.
- 캐시 무효화는 저장 위치가 여러 단계일수록 복잡해진다.

## 핵심 정리

- 캐시는 같은 응답의 반복 전송을 줄인다.
- 만료는 변경과 같지 않으므로 조건부 요청으로 재검증할 수 있다.
- `Last-Modified`는 시각, ETag는 서버가 정한 버전 값으로 비교한다.
- 변경이 없으면 `304`와 헤더만 받고 기존 본문을 재사용한다.
- 캐시 지시어는 저장 가능 여부와 재검증 정책을 구분해서 이해해야 한다.
