# 웹 서버와 WAS 구성 복습

> 정적 파일 처리와 애플리케이션 로직 실행을 어떤 서버가 담당하는지, 시스템을 분리했을 때의 장점을 정리했다.

## 1. 웹 통신의 공통 기반

브라우저와 서버는 HTTP 요청과 응답으로 데이터를 교환한다.

HTTP로 전달되는 대상은 HTML뿐만이 아니다.

- 텍스트와 JSON
- CSS와 JavaScript
- 이미지와 영상
- 파일
- 서버 간 API 데이터

웹 서버와 WAS는 모두 HTTP 기반으로 동작하지만 주로 담당하는 역할이 다르다.

## 2. 웹 서버

웹 서버는 정적 리소스를 제공하는 역할에 강하다.

```text
HTML 파일
CSS
JavaScript
이미지
다운로드 파일
```

대표적인 기능:

- 정적 파일 응답
- 캐시와 압축 설정
- TLS 종료
- 리버스 프록시
- 요청 분산
- 접근 로그

정적 파일은 애플리케이션 코드를 실행하지 않고 바로 제공할 수 있어 효율적이다.

## 3. 웹 애플리케이션 서버

WAS는 HTTP 처리 기능에 더해 프로그램 코드를 실행한다.

```text
요청 파라미터 해석
→ 서비스 로직 실행
→ 데이터베이스 조회
→ 동적 HTML 또는 JSON 생성
→ 응답
```

서블릿 컨테이너, 스레드 풀, 세션과 애플리케이션 배포 같은 실행 환경을 제공한다.

WAS도 정적 리소스를 제공할 수 있어 웹 서버와 기능 경계가 완전히 고정된 것은 아니다.

## 4. WAS와 DB만 사용하는 구성

```text
클라이언트
→ WAS
→ DB
```

구성이 단순해 작은 서비스나 개발 환경에서 시작하기 쉽다.

하지만 WAS가 정적 파일과 업무 로직을 모두 담당하면 다음 문제가 생길 수 있다.

- 정적 리소스 요청도 애플리케이션 서버 자원 사용
- 동적 처리 장애가 전체 응답에 영향
- 애플리케이션 서버 증설 비용 증가
- 외부에 WAS가 직접 노출될 수 있음

## 5. 웹 서버, WAS, DB 분리

```text
클라이언트
→ 웹 서버
   ├→ 정적 리소스 직접 응답
   └→ 동적 요청을 WAS로 전달
         → DB
```

역할을 나누면 정적 요청은 앞단에서 빠르게 처리하고 애플리케이션 서버는 업무 로직에 집중할 수 있다.

웹 서버는 WAS 여러 대로 요청을 분산하거나 장애가 난 인스턴스를 제외하는 앞단 역할도 할 수 있다.

## 6. 분리 구성의 장점

- 정적 파일 처리와 동적 로직 처리의 독립적인 확장
- WAS 장애 시 앞단에서 오류 페이지 제공 가능
- 애플리케이션 서버의 직접 노출 감소
- 캐시, 압축, 인증서 같은 공통 설정 집중
- 여러 WAS로 로드 밸런싱 가능

## 7. 분리한다고 항상 좋은 것은 아님

서버가 하나 더 늘면 운영 복잡도도 증가한다.

- 배포와 설정 관리 대상 증가
- 프록시 헤더와 실제 클라이언트 IP 처리
- 로그가 여러 시스템에 분산
- 네트워크 구간과 장애 지점 추가
- 캐시 무효화 정책 필요

트래픽과 운영 요구가 작다면 WAS 하나로 시작하는 구성이 더 단순할 수 있다.

## 8. 선택 기준

```text
작은 서비스·학습 환경
→ WAS 중심의 단순 구성

정적 트래픽이 많음
→ 웹 서버나 CDN 활용

동적 요청이 많고 가용성이 중요함
→ 웹 서버 + 여러 WAS + DB

전 세계 정적 콘텐츠 제공
→ CDN을 앞단에 추가
```

구성 요소의 이름보다 각 계층이 어떤 책임과 장애 범위를 갖는지 보는 편이 중요하다.

## 핵심 정리

- 웹 서버는 정적 리소스와 프록시 기능에 강하다.
- WAS는 애플리케이션 코드를 실행해 동적 응답을 만든다.
- WAS만으로도 서비스할 수 있지만 역할이 집중될 수 있다.
- 웹 서버를 앞에 두면 정적 처리, 분산, 보안 경계를 나누기 쉽다.
- 계층 분리는 성능과 가용성을 높일 수 있지만 운영 복잡도도 추가한다.
