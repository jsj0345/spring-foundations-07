# HTTP 메서드와 속성 복습

> URI는 대상을 나타내고 HTTP 메서드는 그 대상에 기대하는 행동을 표현한다는 기준으로 정리했다.

## 1. URI에는 리소스를 표현하기

```text
/members
/members/10
/orders/25
```

URI에 `create`, `update`, `delete` 같은 행동을 전부 넣기보다 회원, 주문 같은 리소스를 식별하도록 설계한다.

```text
리소스 → /members/10
행위   → GET, PATCH, DELETE
```

예외적으로 HTML Form 제약이나 특정 명령형 API에서는 컨트롤 URI가 필요할 수 있다.

## 2. GET

```http
GET /members/10
```

리소스를 조회한다. 요청 조건은 보통 쿼리 파라미터로 전달한다.

GET 본문을 기술적으로 처리할 수 있는 환경도 있지만 지원 방식이 일관되지 않을 수 있어 일반적인 조회 데이터는 URI에 표현하는 편이 안전하다.

## 3. POST

```http
POST /members
Content-Type: application/json

{"name":"userA"}
```

요청 본문을 서버가 정한 방식으로 처리하도록 맡긴다.

대표적인 용도는 다음과 같다.

- 새 리소스 등록
- 주문이나 결제 같은 업무 처리
- 다른 메서드로 표현하기 어려운 명령
- 대량 데이터 처리

POST는 단순히 등록만 의미하는 메서드가 아니라 서버 측 처리 요청이라는 더 넓은 의미를 가진다.

## 4. PUT

```http
PUT /members/10
Content-Type: application/json

{
  "name": "userA",
  "age": 20
}
```

대상 URI의 리소스를 전체 대체하는 관점으로 이해한다.

- 대상이 있으면 교체
- 대상이 없으면 생성될 수 있음
- 클라이언트가 대상 URI를 알고 있음

일부 필드를 빠뜨린 채 PUT을 보내면 누락된 값까지 사라질 수 있으므로 전체 표현을 전달하는 API인지 확인해야 한다.

## 5. PATCH

```http
PATCH /members/10
Content-Type: application/json

{"age":21}
```

리소스의 일부만 변경하는 요청에 적합하다.

어떤 필드 변경 형식을 지원하는지는 서버 API 계약에 따라 달라진다.

## 6. DELETE

```http
DELETE /members/10
```

대상 리소스의 제거를 요청한다.

이미 삭제된 리소스에 다시 DELETE를 호출했을 때 어떤 상태 코드를 반환할지는 API 정책에 따라 다를 수 있지만 목표 상태는 대상이 없는 상태로 동일하다.

## 7. 안전성

안전한 메서드는 호출 자체가 대상 리소스의 상태를 변경하지 않는다는 의미다.

대표적으로 GET과 HEAD가 있다.

서버 로그가 쌓이거나 조회 수가 증가하는 부수 효과까지 전혀 없다는 뜻은 아니다. 클라이언트가 요청한 리소스의 업무 상태 변경 여부를 기준으로 본다.

## 8. 멱등성

같은 요청을 여러 번 실행해도 최종 상태가 같다면 멱등하다고 본다.

| 메서드 | 일반적인 멱등성 |
|---|---|
| GET | 멱등 |
| PUT | 멱등 |
| DELETE | 멱등 |
| POST | 보통 멱등 아님 |
| PATCH | 구현에 따라 다름 |

네트워크 오류 뒤 자동 재시도를 설계할 때 멱등성은 중요한 판단 기준이다.

예를 들어 주문 생성 POST를 그대로 재시도하면 중복 주문이 생길 수 있어 별도 요청 식별자나 중복 방지 정책이 필요하다.

## 9. 캐시 가능성

HTTP 규격상 여러 메서드가 캐시 가능할 수 있지만 실제 환경에서는 GET과 HEAD 응답이 주로 캐시된다.

캐시는 메서드 이름만으로 결정되지 않고 응답의 `Cache-Control`, 인증 여부, 중간 캐시 정책 등의 영향을 받는다.

## 핵심 정리

- URI는 리소스를, HTTP 메서드는 행위를 나타낸다.
- GET은 조회, POST는 서버가 정한 처리, PUT은 전체 교체, PATCH는 일부 변경, DELETE는 제거에 사용한다.
- 안전성과 멱등성은 서로 다른 개념이다.
- 멱등성은 장애 상황에서 재시도 가능 여부를 판단하는 데 중요하다.
- PUT과 PATCH는 변경 범위가 다르므로 API 계약을 분명히 해야 한다.
