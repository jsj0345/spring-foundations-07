# HTTP 상태 코드 복습

> 상태 코드를 단순 암기하기보다 요청 결과와 클라이언트의 다음 행동을 알려 주는 신호로 정리했다.

## 1. 상태 코드 범위

| 범위 | 의미 |
|---|---|
| `1xx` | 요청 처리 과정의 정보 |
| `2xx` | 요청 성공 |
| `3xx` | 추가 이동이나 캐시 처리 필요 |
| `4xx` | 클라이언트 요청 문제 |
| `5xx` | 서버 처리 문제 |

클라이언트가 처음 보는 세부 코드를 받더라도 같은 백 단위 범주의 성격으로 해석할 수 있다.

## 2. 주요 성공 코드

### 200 OK

요청이 정상 처리됐고 응답 본문에 결과가 들어갈 수 있다.

### 201 Created

새 리소스가 만들어졌다.

```http
HTTP/1.1 201 Created
Location: /members/101
```

`Location`으로 생성된 리소스 위치를 알려 줄 수 있다.

### 202 Accepted

요청을 접수했지만 실제 처리가 아직 끝나지 않은 비동기 작업에 사용할 수 있다.

### 204 No Content

처리는 성공했지만 응답 본문이 필요 없을 때 사용한다.

## 3. 리다이렉션의 기본 흐름

```http
HTTP/1.1 302 Found
Location: /new-page
```

브라우저는 `Location`이 가리키는 주소로 새 요청을 보낸다.

리다이렉션 코드를 선택할 때는 주소가 영구적으로 바뀌었는지와 원래 메서드를 유지해야 하는지를 구분해야 한다.

## 4. 영구 리다이렉션

### 301 Moved Permanently

리소스 주소가 장기적으로 변경됐음을 나타낸다. 사용자 에이전트에 따라 원래 POST가 GET으로 바뀔 수 있다.

### 308 Permanent Redirect

영구 이동이라는 의미를 가지면서 요청 메서드와 본문을 유지한다.

POST 본문을 새 위치에도 그대로 보내야 하는 상황이라면 308의 의미가 더 명확하다.

## 5. 일시적 리다이렉션

| 코드 | 메서드 처리 |
|---|---|
| `302 Found` | 관행적으로 GET으로 바뀔 수 있음 |
| `303 See Other` | 다음 요청을 GET으로 수행 |
| `307 Temporary Redirect` | 원래 메서드와 본문 유지 |

리다이렉션 뒤에 같은 POST를 다시 보내면 되는지, 결과 페이지를 GET으로 조회해야 하는지에 따라 선택한다.

## 6. PRG 패턴

주문 등록 뒤 브라우저가 POST 응답 화면에 그대로 머물면 새로고침 시 같은 POST가 다시 전송될 수 있다.

```text
POST /orders
→ 주문 생성
→ 303 Location: /orders/100
→ GET /orders/100
```

이 흐름이 Post/Redirect/Get이다.

최종 화면이 GET이 되므로 새로고침해도 조회만 반복되고 등록 요청이 다시 실행되는 위험을 줄인다.

PRG만으로 모든 중복 요청을 막는 것은 아니다. 네트워크 재전송이나 사용자의 반복 클릭에는 서버 측 멱등 키와 중복 검증도 필요할 수 있다.

## 7. 304 Not Modified

조건부 캐시 요청에서 리소스가 바뀌지 않았음을 알려 준다.

응답 본문을 다시 전송하지 않고 클라이언트가 보관한 캐시를 사용하게 한다.

304는 일반적인 성공 본문 응답이 아니라 캐시 재검증 흐름의 코드다.

## 8. 4xx와 5xx 구분

### 4xx

요청 내용이나 권한 등 클라이언트 측에서 수정해야 할 문제가 있다.

- `400 Bad Request`: 형식이나 값이 잘못됨
- `401 Unauthorized`: 인증 필요
- `403 Forbidden`: 인증 여부와 별개로 접근 권한 없음
- `404 Not Found`: 대상 리소스를 찾을 수 없음
- `405 Method Not Allowed`: URI는 있지만 메서드를 지원하지 않음

### 5xx

정상적인 요청을 서버가 처리하지 못한 상황이다.

- `500 Internal Server Error`: 서버 내부 오류
- `503 Service Unavailable`: 일시적으로 처리 불가

업무 검증 실패를 무조건 500으로 반환하면 서버 장애와 사용자 입력 오류를 구분하기 어려워진다.

## 9. 상태 코드 설계 기준

- 클라이언트가 다음에 무엇을 해야 하는가
- 새 리소스 위치를 알려 줘야 하는가
- 인증과 권한 문제를 구분했는가
- 일시적 장애인지 영구적 실패인지
- 재시도해도 되는 요청인지
- 응답 본문에 오류 원인을 얼마나 제공할지

## 핵심 정리

- 상태 코드는 요청 처리 결과와 후속 행동을 전달한다.
- 201은 생성 위치, 204는 본문 없는 성공을 표현할 수 있다.
- 301·308은 영구 이동, 302·303·307은 일시 이동에 사용한다.
- PRG는 POST 뒤 결과 페이지를 GET으로 전환해 새로고침 중복을 줄인다.
- 4xx는 요청 문제, 5xx는 서버 처리 문제로 구분한다.
